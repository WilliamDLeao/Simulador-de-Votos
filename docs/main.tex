\begin{abstract}
Este relatório descreve a implementação e os testes de um sistema de votação eletrônica distribuído, feito para a Prática 1 (Infraestrutura Web e Balanceamento de Carga) da disciplina de Sistemas Operacionais Modernos. O sistema usa quatro contêineres orquestrados com Docker Compose: um proxy reverso Nginx que faz o balanceamento de carga (\texttt{least\_conn} como configuração final, com \textit{Round-Robin} como \textit{baseline} e \textit{IP Hash} avaliados para comparação), duas instâncias idênticas e sem estado (\textit{stateless}) da API de votação em Node.js/Express, e um banco PostgreSQL 15 com volume Docker nomeado para persistência. Todos ficam em uma rede Docker do tipo \textit{bridge}, e só a porta 80 do proxy é exposta ao host. O relatório apresenta os componentes, as decisões de projeto, a alternância entre as instâncias e os testes de persistência e de falha.
\end{abstract}

\section{Introdução}
% ==============================================================================
Uma aplicação centralizada em um único processo tem limites de escalabilidade e um ponto único de falha (\textit{Single Point of Failure}, SPOF). Em um sistema de votação, muitos acessos simultâneos podem esgotar a memória, sobrecarregar a CPU ou travar a escrita em disco, e isso afeta tanto a disponibilidade quanto a confiabilidade da apuração.

Para lidar com isso, o projeto separa o sistema em três camadas, cada uma em seu contêiner: um proxy que recebe e distribui o tráfego, nós de processamento sem estado local e um banco de dados com persistência. A implementação atende aos requisitos da Prática 1:
\begin{enumerate}
    \item \textbf{Orquestração:} um \texttt{docker-compose.yml} sobe os quatro contêineres de forma reprodutível.
    \item \textbf{Proxy reverso:} o Nginx é o único ponto de entrada externo (porta 80) e esconde os nós internos.
    \item \textbf{Balanceamento de carga:} as requisições HTTP são divididas entre duas réplicas idênticas da API Node.js. Cada resposta traz o \textit{hostname} do contêiner e o nome da instância, o que permite saber quem atendeu.
    \item \textbf{Persistência:} o PostgreSQL 15 usa um Docker Volume próprio, então os dados sobrevivem à parada ou recriação do contêiner.
    \item \textbf{Isolamento de rede:} os serviços ficam na rede \textit{bridge} \texttt{rede\_votacao}, sem portas publicadas no host (exceto a 80 do proxy).
\end{enumerate}

\section{Tecnologias Utilizadas e Papel dos Componentes}
% ==============================================================================
Esta seção descreve cada componente do sistema e o que ele faz.

\subsection{Proxy Reverso e Balanceador de Carga (Nginx)}
O contêiner \texttt{proxy\_nginx} usa a imagem \texttt{nginx:alpine} e tem as seguintes funções:
\begin{itemize}
    \item \textbf{Ponto único de entrada:} é o único serviço com porta publicada no host (\texttt{80:80}). Todo o tráfego passa por ele, e as APIs e o banco não ficam acessíveis diretamente.
    \item \textbf{Algoritmo de escalonamento:} a configuração atual usa \texttt{least\_conn} (Seção~4.3), que envia a requisição para o backend com menos conexões ativas no momento. Como as escritas no banco têm latência variável, isso evita sobrecarregar uma réplica que já está ocupada. O \texttt{ip\_hash} (Seção~4.3.1) foi testado, mas não foi adotado: as APIs são \textit{stateless}, o roteiro pede alternância entre as aplicações no navegador e a afinidade manda todo o tráfego de um mesmo cliente para uma única réplica. Os dois algoritmos, mais o \textit{Round-Robin} como \textit{baseline}, foram medidos (Seções~4.3 e 4.3.1).
    \item \textbf{Detecção passiva de falhas:} as réplicas estão no bloco \texttt{upstream} com \texttt{max\_fails=3} e \texttt{fail\_timeout=5s}. Se uma instância falhar três vezes dentro da janela de 5 s (não precisam ser seguidas), o Nginx a tira do escalonamento por esse período e manda o tráfego para a outra.
    \item \textbf{Conexões persistentes:} usa \texttt{keepalive 32} e HTTP/1.1 com o cabeçalho \texttt{Connection} limpo (\texttt{proxy\_set\_header Connection ""}), reaproveitando conexões TCP com o backend e evitando \textit{handshakes} repetidos.
    \item \textbf{Cabeçalho de auditoria:} o Nginx adiciona \texttt{X-Upstream-Backend \$upstream\_addr} às respostas, o que permite ver qual backend atendeu cada requisição.
\end{itemize}

\subsection{Orquestração com Docker Engine e Docker Compose}
O ciclo de vida dos contêineres e a infraestrutura são definidos no \texttt{docker-compose.yml} (\textit{Infrastructure as Code}):
\begin{itemize}
    \item \textbf{Isolamento no nível do SO:} os contêineres compartilham o kernel do host e usam \textit{namespaces} (PID, IPC, rede, pontos de montagem) para isolamento e \textit{cgroups} para controlar CPU e memória.
    \item \textbf{Reinício automático:} todos os serviços usam \texttt{restart: always}, então o Docker os reinicia se terminarem com falha ou quando a máquina for reiniciada.
    \item \textbf{Ordem de inicialização:} \texttt{depends\_on} define que as APIs sobem depois do banco (\texttt{db}) e o proxy depois das APIs (\texttt{api1} e \texttt{api2}).
\end{itemize}

\subsection{Rede Virtual Isolada (Docker Network)}
A rede privada \texttt{rede\_votacao} usa o driver \texttt{bridge}:
\begin{itemize}
    \item \textbf{DNS interno:} o Docker resolve os nomes dos serviços (\texttt{api1}, \texttt{api2}, \texttt{db}, \texttt{nginx}) para os IPs dos contêineres, sem precisar de endereços fixos.
    \item \textbf{Resolução dos upstreams:} o Nginx resolve \texttt{api1} e \texttt{api2} na inicialização (ou no \textit{reload}) e guarda os endereços. Se um contêiner voltar com outro IP depois de um \texttt{docker start}, é preciso recarregar ou recriar o proxy; só a atualização do DNS interno não muda o \texttt{upstream} já carregado.
    \item \textbf{Portas internas:} as portas das APIs (5000) e do PostgreSQL (5432) não são publicadas e só podem ser acessadas de dentro da rede \texttt{rede\_votacao}.
\end{itemize}

\subsection{Persistência com Docker Volume}
Os dados do banco ficam no volume \texttt{pgdata}:
\begin{itemize}
    \item \textbf{Ciclo de vida independente:} os dados ficam no volume, fora da camada de escrita (\textit{Copy-on-Write}) do contêiner. Por isso, \texttt{docker stop} e \texttt{docker rm} preservam as tabelas e os registros. Numa falha abrupta (\texttt{docker kill}) o PostgreSQL recupera o estado pelo WAL, mas esse cenário não foi testado aqui. O teste usou \texttt{docker stop}, que envia SIGTERM e permite um desligamento limpo, então ele valida a persistência e não uma queda do SGBD.
    \item \textbf{E/S:} o volume não passa pelo driver de armazenamento em camadas do Docker (tradicionalmente \textit{overlay2}; neste host, com Docker~29 e containerd, o \texttt{docker info} mostra \texttt{overlayfs}, conforme a Tabela~\ref{tab:ambiente}) e acessa o sistema de arquivos do host diretamente.
\end{itemize}

\subsection{Microsserviços de Backend (Node.js e Express)}
O backend foi escrito em JavaScript sobre Node.js (imagem \texttt{node:20-alpine}, versão v20.20.2 conferida nos contêineres):
\begin{itemize}
    \item \textbf{E/S não bloqueante:} usa o \textit{event loop} do Node.js e um pool de conexões com a biblioteca \texttt{pg} (máximo de 10 conexões por instância).
    \item \textbf{Sem estado:} as instâncias não guardam sessões nem contagens na memória do processo. Toda operação vai para o banco, então qualquer réplica pode atender qualquer requisição.
    \item \textbf{Identificação da instância:} o backend lê a variável de ambiente \texttt{INSTANCE\_NAME} e chama \texttt{os.hostname()}, e inclui os dois valores em todas as respostas JSON, o que permite conferir o balanceamento.
    \item \textbf{Rotas:}
    \begin{itemize}
        \item \texttt{GET /}: \textit{health check}, com teste de conexão ao banco via \texttt{SELECT 1}.
        \item \texttt{GET /candidatos}: lista os candidatos e seus totais parciais.
        \item \texttt{POST /votar}: registra o voto. Uma \textit{Common Table Expression} (CTE) atualiza o contador em \texttt{candidatos} e grava o registro em \texttt{votos} numa única instrução SQL.
        \item \texttt{GET /apuracao}: calcula o percentual de votos de cada candidato em relação ao total.
    \end{itemize}
\end{itemize}

\subsection{Sistema Gerenciador de Banco de Dados (PostgreSQL 15)}
O contêiner \texttt{db\_postgres} (\texttt{postgres:15-alpine}) cuida da persistência e das transações:
\begin{itemize}
    \item \textbf{ACID:} garante atomicidade, consistência, isolamento e durabilidade mesmo com votos concorrentes.
    \item \textbf{Contenção no contador:} o \texttt{POST /votar} executa um \texttt{UPDATE candidatos SET total\_votos = total\_votos + 1} na linha do candidato. Esse incremento serializa as escritas concorrentes no mesmo candidato: o isolamento evita perda de votos, mas é o gargalo esperado sob carga de escrita. Essa contenção \textbf{não foi medida} nos testes de desempenho deste relatório, que usam apenas \texttt{GET /} (ver Seção~4.3).
    \item \textbf{Carga inicial:} o script \texttt{database/init.sql} é montado como somente leitura (\texttt{:ro}) em \texttt{/docker-entrypoint-initdb.d/init.sql}. Na primeira inicialização, o contêiner cria as tabelas e insere os candidatos de teste (Trecho~\ref{code:init_sql}).
\end{itemize}

\begin{lstlisting}[language=SQL, caption={Inicialização do banco de dados (\texttt{database/init.sql})}, label={code:init_sql}]
CREATE TABLE IF NOT EXISTS candidatos (
    id SERIAL PRIMARY KEY,
    numero INT UNIQUE NOT NULL,
    nome VARCHAR(100) NOT NULL,
    partido VARCHAR(50) NOT NULL,
    total_votos INT DEFAULT 0
);

CREATE TABLE IF NOT EXISTS votos (
    id SERIAL PRIMARY KEY,
    candidato_id INT REFERENCES candidatos(id),
    instancia_origem VARCHAR(50) NOT NULL,
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO candidatos (numero, nome, partido, total_votos) VALUES
(10, 'Candidato A', 'Partido A', 0),
(20, 'Candidato B', 'Partido B', 0),
(99, 'Voto Nulo / Branco', 'Nenhum', 0)
ON CONFLICT (numero) DO NOTHING;
\end{lstlisting}

As principais decisões de projeto foram:
\begin{itemize}
    \item \textbf{Tabela de registros mais contador:} cada voto insere uma linha em \texttt{votos} (com horário e instância de origem) e incrementa \texttt{candidatos.total\_votos}. Assim o \texttt{GET /apuracao} lê o contador direto, sem precisar de um \texttt{COUNT(*)} a cada consulta.
    \item \textbf{Consistência via CTE:} o \texttt{UPDATE} e o \texttt{INSERT} acontecem na mesma instrução SQL, então a soma de \texttt{candidatos.total\_votos} fica sempre igual ao número de registros em \texttt{votos}.
    \item \textbf{Inicialização repetível:} \texttt{CREATE TABLE IF NOT EXISTS} e \texttt{INSERT ... ON CONFLICT (numero) DO NOTHING} evitam erro ou duplicação se o script rodar de novo. Vale lembrar que o PostgreSQL só executa o conteúdo de \texttt{/docker-entrypoint-initdb.d/} quando o volume \texttt{pgdata} está vazio.
\end{itemize}

\subsubsection{Limitações Conhecidas e Melhorias Possíveis}
\begin{itemize}
    \item \textbf{Credenciais no manifesto:} usuário e senha (\texttt{postgres}/\texttt{postgres}) estão em texto puro no \texttt{docker-compose.yml}. Isso serve para o trabalho acadêmico, mas em produção o ideal seria usar \textit{Docker secrets} ou um \texttt{.env} fora do versionamento, com um usuário de privilégios mínimos.
    \item \textbf{Sem \texttt{healthcheck} no banco:} o \texttt{depends\_on} só espera o contêiner \texttt{db} subir, não o PostgreSQL ficar pronto. Um \texttt{healthcheck} com \texttt{pg\_isready} evitaria erros de conexão na partida.
    \item \textbf{\texttt{candidato\_id} sem \texttt{NOT NULL}:} a CTE sempre preenche a chave estrangeira, mas adicionar \texttt{NOT NULL} no esquema reforçaria a integridade no próprio banco.
\end{itemize}

O \texttt{least\_conn} ficou como configuração final, o que atende ao requisito de alternância do roteiro. O \texttt{ip\_hash} foi avaliado como extra (Seção~4.3.1) e não foi adotado, e o \textit{Round-Robin} fica documentado como baseline.

Esses números vêm de execuções curtas no mesmo host e mostram funcionamento e tendência, não um \textit{benchmark} rigoroso. O script mede a latência de ponta a ponta no cliente, incluindo a conexão e o \textit{keepalive} do Nginx. A ordem das medições (\textit{Round-Robin} primeiro, \texttt{least\_conn} depois) é um viés conhecido do experimento.

Além disso, todas as medições acima usam \texttt{GET /}. Elas não captam a contenção de escrita do \texttt{POST /votar}, cujo \texttt{UPDATE} na mesma linha de \texttt{candidatos} serializa os incrementos (Seção~3.6). O benefício do \texttt{least\_conn} para cargas de escrita vem do princípio de desviar conexões ativas, mas não foi quantificado aqui.

\subsubsection{Avaliação experimental: \textit{IP Hash} (afinidade por cliente)}
Como complemento, a diretiva \texttt{least\_conn;} foi trocada por \texttt{ip\_hash;} no bloco \texttt{upstream} (com \texttt{scripts/trocar\_algoritmo.sh}). O \texttt{ip\_hash} calcula um hash do IP de origem (os três primeiros octetos, no caso de IPv4) e sempre encaminha o cliente para a mesma réplica, o que dá afinidade de sessão (\textit{session affinity}). A configuração efetiva foi conferida dentro do contêiner antes da coleta:
\begin{lstlisting}[language=bash]
docker exec proxy_nginx nginx -T | grep -A6 'upstream simulador_votacao'
# upstream simulador_votacao {
#     ip_hash;
#     server api1:5000 max_fails=3 fail_timeout=5s;
#     server api2:5000 max_fails=3 fail_timeout=5s;
#     keepalive 32;
# }
\end{lstlisting}

Na versão inicial usada na coleta de 20/11/2026, o \texttt{trocar\_algoritmo.sh} editava o arquivo com \texttt{sed -i}, que troca o inode do arquivo. Como o \texttt{nginx.conf} entra no contêiner por \textit{bind mount} (\texttt{./nginx/nginx.conf:/etc/nginx/nginx.conf:ro}), o contêiner continuava vendo o inode antigo mesmo depois do \texttt{nginx -s reload}, e foi preciso recriar o proxy (\texttt{docker compose up -d --force-recreate nginx}). Depois o script foi corrigido para gravar as alterações em um arquivo temporário (\texttt{mktemp}) e escrever o resultado com \texttt{cat "\$TMP" > "\$CONF"}, o que preserva o inode e faz o \texttt{nginx -s reload} funcionar normalmente.

O \texttt{ip\_hash} troca a distribuição uniforme por previsibilidade na origem. Com um único IP de teste, toda a carga vai para uma réplica (100\% na \texttt{Instancia-2}). O \texttt{least\_conn} segue ativo, e \texttt{ip\_hash} e \textit{Round-Robin} ficam documentados como alternativas avaliadas. O teste de parada da réplica fixa mostra a detecção passiva: diferente do teste da Seção~4.5, aqui havia uma réplica alternativa para onde o tráfego podia ir mesmo com a afinidade ativa. Como antes, esses números são de execuções curtas no mesmo host (20/11/2026) e mostram só o funcionamento, não um \textit{benchmark} rigoroso. A concentração em uma única instância acontece porque todo o tráfego de teste vem de \texttt{localhost}.

\subsection{Teste de Falha de um Contêiner Individual}
Além da parada do banco (Seção~4.4), o script \texttt{scripts/demo\_falha\_container.sh} testa a falha de qualquer um dos quatro contêineres (\texttt{proxy\_nginx}, \texttt{api\_instancia\_1}, \texttt{api\_instancia\_2} e \texttt{db\_postgres}). Com a stack no ar, ele é executado a partir da raiz do projeto:
\begin{lstlisting}[language=bash]
bash scripts/demo_falha_container.sh [container] [votos]
bash scripts/demo_falha_container.sh                  # padrao: api_instancia_1, 20 votos
bash scripts/demo_falha_container.sh api_instancia_2 50
\end{lstlisting}
O script mostra o estado inicial, registra a contagem de votos, executa \texttt{docker stop} no alvo, envia votos pela porta 80 durante a falha, confere se os outros contêineres continuam ativos, reinicia o alvo e compara a contagem final com o valor esperado (\texttt{antes + confirmados}). Na execução de 20/11/2026 o algoritmo ativo era o \texttt{least\_conn} e o alvo foi a \texttt{api\_instancia\_1}. Como só a \texttt{api\_instancia\_2} restava no \texttt{upstream}, ela era a única rota possível para os 20 votos. O teste mostra que o serviço continuou funcionando, mas não isola o efeito de \texttt{max\_fails}/\texttt{fail\_timeout}. A evidência da detecção passiva está no teste da Seção~4.3.1, em que a réplica fixada pelo \texttt{ip\_hash} foi parada e o tráfego migrou para a outra e depois voltou.

Ele não prova, sozinho, que \texttt{max\_fails}/\texttt{fail\_timeout} isolaram a réplica, já que com uma única instância saudável no \texttt{upstream} qualquer algoritmo a escolheria. \subsection{Isolamento de Rede}
Para verificar o isolamento da \texttt{rede\_votacao}, foi feita uma tentativa de conexão direta do host às portas internas dos serviços:
\begin{lstlisting}[language=bash]
# Tentativa de conexao direta com a API
curl http://localhost:5000/
# curl: (7) Failed to connect to localhost:5000 after 0 ms: Could not connect to server

# Tentativa de conexao direta com o PostgreSQL
curl http://localhost:5432
# curl: (7) Failed to connect to localhost:5432 after 0 ms: Could not connect to server

# Controle: porta publica do proxy
curl -o /dev/null -w 'HTTP %{http_code}\n' http://localhost/
# HTTP 200
\end{lstlisting}
As conexões foram recusadas na hora (\texttt{after 0 ms}): as portas \texttt{5000} e \texttt{5432} não têm \texttt{ports:} no \texttt{docker-compose.yml}, então não há \textit{socket} escutando no host. O acesso à API e ao banco só é possível pelo proxy na porta 80 (controle: \texttt{HTTP 200}), o que cumpre o requisito de isolamento. O cabeçalho \texttt{X-Upstream-Backend} também foi conferido nas respostas do proxy (por exemplo, \texttt{X-Upstream-Backend: 172.18.0.4:5000}).

\section{Conclusão}
% ==============================================================================
Esta prática permitiu aplicar conceitos de Sistemas Operacionais Modernos e de microsserviços distribuídos. Ficou claro como \textit{namespaces} e \textit{cgroups} permitem criar ambientes isolados, leves e reprodutíveis, sem o peso de máquinas virtuais tradicionais.

A separação entre as camadas foi importante para o resultado: o Nginx recebe o tráfego e distribui com \textit{Least Connections} (o \textit{IP Hash} foi avaliado como extra e não adotado), os nós Node.js não guardam estado e o PostgreSQL 15 mantém os dados em um Docker Volume. Isso deu disponibilidade, tolerância a falhas e proteção da rede interna. Nos testes de 19/11/2026, no notebook Acer Nitro ANV15-51 (Seção~4.2 e Tabela~\ref{tab:ambiente}), a alternância ficou em 50/50 entre as instâncias e o \texttt{least\_conn} distribuiu de forma adaptativa (54/46 a 56/44). Ele teve latência média menor (5,02 ms contra 9,30 ms) e vazão maior (1706,6 contra 1097,7 req/s), embora parte da diferença venha do \textit{cold start} do baseline, medido primeiro (Seção~4.3). Em 20/11/2026, o \texttt{ip\_hash} foi avaliado (Seção~4.3.1): as 50 requisições de cada repetição foram todas atendidas pela \texttt{Instancia-2} (100\%), como esperado quando todo o tráfego sai de um único IP, e o teste de falha da réplica fixa confirmou a detecção passiva do Nginx. A afinidade não foi mantida, porque as APIs são \textit{stateless}, o roteiro exige alternância no navegador e um único cliente concentraria toda a carga em uma réplica. O teste de persistência manteve os 2572 votos depois do \texttt{docker stop} e do \texttt{docker start} do banco, e o teste de isolamento confirmou que as portas internas não aceitam acesso direto. O sistema atende aos requisitos da Prática 1.
