\begin{abstract}
Este relatório documenta a concepção, a implementação e a validação experimental de uma infraestrutura distribuída para um sistema de votação eletrônica de alta disponibilidade, desenvolvida em conformidade com as diretrizes da \textbf{Prática 1: Infraestrutura Web e Balanceamento de Carga} da disciplina de Sistemas Operacionais Modernos. A arquitetura implementada organiza quatro contêineres interdependentes orquestrados via Docker Compose: um Proxy Reverso e balanceador de carga Nginx configurado com o algoritmo \textit{Least Connections} (\texttt{least\_conn}), duas instâncias homogêneas e sem estado (\textit{stateless}) da API de votação desenvolvidas em Node.js/Express, e um Sistema Gerenciador de Banco de Dados relacional PostgreSQL 15 munido de persistência durável via Docker Volume nomeado e isolamento estrito de portas através de uma Docker Network em modo \textit{bridge}. Este documento registra minuciosamente o que foi efetivamente implementado até o momento, descrevendo os componentes, as decisões arquiteturais de sistemas operacionais, as evidências de alternância de nós e os procedimentos de validação de persistência e tolerância a falhas.
\end{abstract}

\section{Introdução}
% ==============================================================================
Em ambientes computacionais modernos e de missão crítica, aplicações monolíticas centralizadas em processos únicos enfrentam severas limitações de escalabilidade vertical e suscetibilidade a pontos únicos de falha (\textit{Single Points of Failure} --- SPOF). No contexto de um sistema de votação eletrônica, oscilações bruscas de demanda e acessos simultâneos massivos podem levar ao esgotamento de memória, sobrecarga da CPU ou bloqueios de operações de escrita em disco, comprometendo a disponibilidade do serviço e a confiabilidade da apuração eleitoral.

Para superar esses entraves com base nos conceitos teóricos de Sistemas Operacionais Modernos, foi projetado e implantado um ecossistema conteinerizado baseado em microsserviços. A solução adota a divisão funcional entre recepção e balanceamento de tráfego, nós de processamento concorrente desacoplados de estado local e persistência transacional durável.

A implementação atual atende integralmente aos requisitos estipulados para a Prática 1:
\begin{enumerate}
    \item \textbf{Orquestração Unificada:} Um manifesto \texttt{docker-compose.yml} parametrizado que provisiona quatro contêineres de maneira coordenada e reprodutível.
    \item \textbf{Proxy Reverso de Borda:} Servidor Nginx atuando como único ponto de ingresso externo (porta 80), ocultando os nós internos.
    \item \textbf{Balanceamento de Carga:} Distribuição dinâmica de requisições HTTP entre duas réplicas idênticas da API Node.js, com identificação rastreável do nó executor por meio do \textit{hostname} do contêiner e nome de instância.
    \item \textbf{Persistência e Isolamento de Armazenamento:} Banco de dados relacional PostgreSQL 15 configurado com Docker Volume independente para garantir a durabilidade dos dados eleitorais contra encerramentos forçados ou recriação de contêineres.
    \item \textbf{Segurança e Isolamento de Rede:} Rede virtual privada em modo \textit{bridge} (\texttt{rede\_votacao}), na qual os serviços de backend e banco de dados operam de forma isolada, sem portas abertas na interface do hospedeiro (\textit{host}).
\end{enumerate}

\section{Tecnologias Utilizadas e Papel dos Componentes}
% ==============================================================================
Nesta seção, descrevem-se os componentes do sistema implementado, destacando sua fundamentação técnica em sistemas operacionais e o papel desempenhado no ecossistema.

\subsection{Proxy Reverso e Balanceador de Carga (Nginx)}
O contêiner \texttt{proxy\_nginx} utiliza a distribuição leve \texttt{nginx:alpine}. Ele cumpre múltiplos papéis na fronteira do sistema:
\begin{itemize}
    \item \textbf{Encapsulamento de Borda:} Constitui o único serviço com bind de porta na interface de rede externa do hospedeiro (\texttt{80:80}). Todo o tráfego de clientes é concentrado nele, protegendo os nós de backend e o banco de dados de exposição pública direta.
    \item \textbf{Algoritmo \textit{Least Connections} (\texttt{least\_conn}):} Em vez de empregar o algoritmo determinístico de rotação estrita (\textit{Round-Robin}), o Nginx foi configurado com a diretiva \texttt{least\_conn}. Esse algoritmo aloca requisições prioritariamente ao nó de backend que mantiver o menor número de conexões HTTP ativas naquele instante. Em sistemas transacionais de votação, onde transações de escrita no banco introduzem latências variáveis, o \textit{Least Connections} previne a saturação de uma réplica momentaneamente atarefada.
    \item \textbf{Tolerância a Falhas e Detecção Passiva:} As réplicas foram declaradas no bloco \texttt{upstream} com os parâmetros \texttt{max\_fails=3} e \texttt{fail\_timeout=5s}. Caso uma das instâncias da API deixe de responder consecutivamente por três tentativas, o Nginx a isola do escalonamento pelo intervalo estipulado, encaminhando todo o fluxo para a instância saudável.
    \item \textbf{Otimização de Transporte e Conexões Persistentes:} Implementa \texttt{keepalive 32} e força o protocolo \texttt{HTTP/1.1} com cabeçalho de conexão limpo (\texttt{proxy\_set\_header Connection ""}), reaproveitando conexões TCP pré-estabelecidas com o backend e minimizando o custo de sucessivos \textit{handshakes} no sistema operacional.
    \item \textbf{Metadados para Auditoria:} O Nginx injeta nas respostas o cabeçalho \texttt{X-Upstream-Backend \$upstream\_addr}, viabilizando auditoria transparente do balanceamento pelo cliente.
\end{itemize}

\subsection{Orquestração com Docker Engine e Docker Compose}
A gestão do ciclo de vida dos contêineres e a definição da infraestrutura como código (\textit{Infrastructure as Code} --- IaC) foram concretizadas via \texttt{docker-compose.yml}:
\begin{itemize}
    \item \textbf{Isolamento em Nível de SO:} Contêineres compartilham o kernel hospedeiro utilizando \textit{Namespaces} para isolamento de PID, IPC, rede e pontos de montagem, e \textit{cgroups} para contabilidade de recursos de processamento e memória RAM.
    \item \textbf{Políticas de Recuperação:} Todos os serviços receberam a diretiva \texttt{restart: always}, instruindo o daemon do Docker a reiniciar automaticamente contêineres que terminem com falha ou durante reinícios da máquina hospedeira.
    \item \textbf{Dependências de Inicialização:} Foi estipulada a ordem de subida dos serviços através de \texttt{depends\_on}: as APIs dependem do contêiner de banco de dados (\texttt{db}), e o proxy reverso depende das réplicas da aplicação (\texttt{api1} e \texttt{api2}).
\end{itemize}

\subsection{Rede Virtual Isolada (Docker Network)}
Foi criada a rede virtual privativa \texttt{rede\_votacao} utilizando o driver \texttt{bridge}:
\begin{itemize}
    \item \textbf{Resolução de Nomes via DNS Interno:} O daemon do Docker provê um resolvedor DNS interno que traduz os nomes dos serviços (\texttt{api1}, \texttt{api2}, \texttt{db}, \texttt{nginx}) para seus respectivos endereços IP virtuais dinâmicos, eliminando dependências rígidas de endereçamento estático.
    \item \textbf{Blindagem de Portas de Backend:} As portas das APIs (5000) e do PostgreSQL (5432) foram omitidas da seção de publicação externa, sendo roteáveis exclusivamente dentro do namespace da rede virtual \texttt{rede\_votacao}.
\end{itemize}

\subsection{Persistência com Docker Volume}
A persistência do banco de dados relacional foi implementada com o volume gerenciado \texttt{pgdata}:
\begin{itemize}
    \item \textbf{Independência do Ciclo de Vida:} O armazenamento físico dos dados transacionais do banco reside no volume gerenciado no host, desacoplado da camada efêmera de escrita (\textit{Copy-on-Write}) do contêiner do SGBD. Comandos de parada forçada (\texttt{docker stop}) ou remoção e recriação do contêiner (\texttt{docker rm}) preservam a integridade dos dados e das tabelas intactas.
    \item \textbf{Eficiência de E/S:} O volume ignora os drivers de armazenamento em camadas do Docker (\textit{overlay2}), comunicando-se diretamente com o subsistema de arquivos do sistema hospedeiro.
\end{itemize}

\subsection{Microsserviços de Backend (Node.js e Express)}
Os nós de processamento foram desenvolvidos em JavaScript sob o ambiente de execução Node.js (imagem \texttt{node:18-alpine}):
\begin{itemize}
    \item \textbf{Arquitetura Orientada a Eventos e I/O Não Bloqueante:} Utiliza o \textit{Event Loop} do Node.js e um pool gerenciado de conexões de banco de dados com a biblioteca \texttt{pg} (tamanho máximo de 10 conexões concorrentes por instância).
    \item \textbf{Modelo Rigorosamente \textit{Stateless}:} As instâncias não gravam sessões ou contagens parciais na memória local do processo. Toda operação é atômica e transferida ao banco de dados relacional, permitindo que qualquer réplica atenda a qualquer requisição sem risco de inconsistência.
    \item \textbf{Identificação de Contêineres:} O backend coleta dinamicamente as variáveis de ambiente (\texttt{INSTANCE\_NAME}) e a chamada de sistema \texttt{os.hostname()}, anexando tais metadados em todas as respostas HTTP JSON para fins de validação do balanceamento.
    \item \textbf{Rotas Implementadas:}
    \begin{itemize}
        \item \texttt{GET /}: Validação de integridade (\textit{Health Check}) e teste de conectividade com o banco via \texttt{SELECT 1}.
        \item \texttt{GET /candidatos}: Consulta dos candidatos cadastrados e de seus totais parciais de votos.
        \item \texttt{POST /votar}: Computação atômica do voto. Utiliza uma \textit{Common Table Expression} (CTE) em SQL para atualizar o contador da tabela \texttt{candidatos} e gravar o registro histórico em \texttt{votos} em um único \textit{round-trip} transacional.
        \item \texttt{GET /apuracao}: Cálculo dinâmico do percentual de votos recebidos por candidato em relação ao montante global de votos computados.
    \end{itemize}
\end{itemize}

\subsection{Sistema Gerenciador de Banco de Dados (PostgreSQL 15)}
A persistência durável e o controle transacional do sistema fundamentam-se no contêiner \texttt{db\_postgres} (\texttt{postgres:15-alpine}):
\begin{itemize}
    \item \textbf{Garantias ACID:} Fornece Atomicidade, Consistência, Isolamento e Durabilidade mesmo sob intensa submissão concorrente de votos.
    \item \textbf{Carga de Inicialização Automatizada:} O script \texttt{database/init.sql} é montado em modo somente leitura (\texttt{:ro}) no diretório especial \texttt{/docker-entrypoint-initdb.d/init.sql}. Ao iniciar pela primeira vez, o contêiner cria as tabelas estruturadas e popula os candidatos de teste, conforme demonstrado no Trecho~\ref{code:init_sql}.
\end{itemize}

\begin{lstlisting}[language=SQL, caption={Estrutura de inicialização do banco de dados (\texttt{database/init.sql})}, label={code:init_sql}]
CREATE TABLE IF NOT EXISTS candidatos (
    id SERIAL PRIMARY KEY,
    numero INT UNIQUE NOT NULL,
    nome VARCHAR(100) NOT NULL,
    partido VARCHAR(50) NOT NULL,
    total_votos INT DEFAULT 0
);

CREATE TABLE IF NOT EXISTS votos (
    id SERIAL PRIMARY KEY,
    candidato_id INT REFERENCES candidatos(id),
    instancia_origem VARCHAR(50) NOT NULL,
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO candidatos (numero, nome, partido, total_votos) VALUES
(10, 'Candidato A', 'Partido A', 0),
(20, 'Candidato B', 'Partido B', 0),
(99, 'Voto Nulo / Branco', 'Nenhum', 0)
ON CONFLICT (numero) DO NOTHING;
\end{lstlisting}

\subsection{Avaliação Comparativa: \textit{Least Connections} versus \textit{Round-Robin}}
O roteiro prático solicita a avaliação dos algoritmos de escalonamento tendo como referência (\textit{baseline}) o método \textit{Round-Robin}:
\begin{itemize}
    \item \textbf{Round-Robin (Baseline):} Distribui requisições em ordem cíclica alternada estrita ($1 \rightarrow 2 \rightarrow 1 \rightarrow 2$). Assume a premissa de que todas as requisições consomem exatamente o mesmo tempo de CPU e I/O. Caso a Instância 1 receba uma consulta pesada e demorada (ex.: agregação complexa de votos), o Round-Robin continuará despachando a próxima requisição par para ela, gerando acúmulo de requisições na fila de conexões daquela réplica.
    \item \textbf{Least Connections (\texttt{least\_conn} --- Implementado):} Monitora as conexões ativas estabelecidas pelo proxy com cada nó de backend. A nova requisição é roteada para a instância com menor carga concorrente no instante da chegada. Diante de tempos de resposta heterogêneos do banco de dados, o \textit{Least Connections} provou ser superior por equalizar o estresse dos recursos da máquina hospedeira.
\end{itemize}

A comutação entre algoritmos pode ser realizada de forma limpa sem interrupção de serviço, bastando comentar a diretiva \texttt{least\_conn;} em \texttt{nginx/nginx.conf} e recarregar os processos de trabalho via:
\begin{lstlisting}[language=bash]
docker exec proxy_nginx nginx -s reload
\end{lstlisting}

\subsection{Comprovação da Persistência de Dados e Tolerância a Falhas}
O teste de resiliência e validação do Docker Volume seguiu a seguinte sequência operacional:

\begin{enumerate}
    \item \textbf{Registro de Votos:} Foram efetuadas requisições de voto para os candidatos através da rota \texttt{POST /votar}:
    \begin{lstlisting}[language=bash]
    curl -X POST http://localhost/votar -H "Content-Type: application/json" -d '{"numero": 10}'
    curl -X POST http://localhost/votar -H "Content-Type: application/json" -d '{"numero": 20}'
    \end{lstlisting}
    
    \item \textbf{Consulta de Apuração Inicial:} A chamada a \texttt{GET /apuracao} confirmou os votos persistidos no banco de dados.
    
    \item \textbf{Derrubada Forçada do SGBD:} O contêiner de banco de dados foi deliberadamente finalizado com:
    \begin{lstlisting}[language=bash]
    docker stop db_postgres
    \end{lstlisting}
    
    \item \textbf{Comportamento da Aplicação Sob Falha:} Ao consultar a API com o banco fora do ar, o backend lidou com o erro de forma graciosa através do manipulador \texttt{respostaErroBanco}, retornando código de status \texttt{HTTP 503 Service Unavailable} com mensagem explicativa estruturada em JSON, demonstrando tratamento defensivo sem travamento dos processos Node.js:
    \begin{lstlisting}[language=bash]
    HTTP/1.1 503 Service Unavailable
    {
      "sucesso": false,
      "mensagem": "Banco de dados temporariamente indisponivel",
      "processadoPor": { "instancia": "Instancia-1" }
    }
    \end{lstlisting}

    \item \textbf{Recuperação do Contêiner:} O serviço do banco de dados foi reiniciado:

\section{Conclusão}
% ==============================================================================
A execução desta etapa prática consolidou na prática os conceitos fundamentais de Sistemas Operacionais Modernos e arquitetura de microsserviços distribuídos. Observou-se como a conteinerização baseada em \textit{Namespaces} e \textit{cgroups} permite instanciar ambientes de computação isolados, leves e reprodutíveis sem o peso computacional de máquinas virtuais tradicionais.

O desacoplamento estrito entre camadas --- delegando ao Nginx a função de porteiro de borda com escalonamento por menor número de conexões (\textit{Least Connections}), aos nós de backend Node.js o papel de executores sem estado (\textit{stateless}), e ao PostgreSQL 15 a responsabilidade de persistência durável via Docker Volume --- assegurou alta disponibilidade, tolerância ativa a falhas e proteção de rede interna. O sistema desenvolvido atende plenamente a todos os requisitos solicitados para a Prática 1.
